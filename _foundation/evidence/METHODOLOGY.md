# FIre 消防技能系列 · 方法学说明

> 这份文档说明的不是"技能怎么用"，而是"这一系列为什么是这样做出来的"。
> 任何引用本系列结论的人，都可以据此判断它适用于什么、不适用于什么。

版本：1.0.0　｜　更新：2026-09-07

---

## 一、问题起点

消防领域的自动化工具长期卡在一个尴尬位置：

一类是**条文检索**——把法规原文搬给用户，读不读得懂、用不用得上，工具不管。
另一类是**经验生成**——模型凭语感写一份"看起来很专业"的预案或整改清单，条款来源经不起追问，条文废止了还在引用（比如 GB 35181-2017 已于 2025-11-01 废止，GB 50444-2008"出厂满 5 年首修"已被 GB 55036-2022 覆盖，这两处错误在网上流传的模板里极为常见）。

前者太保守，后者太危险。消防是出了事要追责的领域，编造的条文比没有条文更糟。

FIre 系列的定位是第三条路：**把可核验的法规条文变成可执行的判断规则，让工具敢下结论，同时让每一条结论都能被查证。**

---

## 二、四条设计约束

### 1. 引用必须有出处，宁可留白不可编造

- 每一条规则都挂 `citation`（完整条文表述）与 `citation_code`（简短代号），并在输出报告中一并展示，用户不需要回头翻规则库。
- 权威引用集中维护在 `citation-manifest.json`，共 28 条，全部标注发布机构、文号、施行日期、现行状态与公开查证入口。
- **文号存疑的条目，宁可不写文号。** 例如社会单位消防安全"四个能力"，各地转发件文号不一致，本系列只写能力项本身并注明"以属地公布文本为准"，不编造任何文号。
- **状态必须写明。** GB/T 26875.10-2026 尚未实施（2027-05-01 施行），技能内一律标注"即将实施"；《消防控制室远程控制管理规范》仍是征求意见稿，只作趋势参考、不作判定依据。
- 自动化核验：`verify_all.py` 遍历全部规则库，统计出处标注覆盖率并要求 100%，任何一条规则挂不上权威清单即判定失败。

### 2. 主动，但不骚扰

主动指的是**主动暴露缺口**，不是主动推销：

- 输入信息不全时，明确指出"缺什么、为什么需要、补上之后结论会怎么变"，而不是默默给一个默认值。
- 红线问题置顶展示，附条款依据与罚则，不藏在报告末尾。
- 行动清单**强制封顶**（一般 6~10 条）。一口气甩三十条整改项，等于什么都没说。
- 超出能力范围时直接说"这个判断我做不了，原因是……"，并给出去哪里找答案。

### 3. 确定性优先于聪明

- 全部引擎为纯规则实现，不含随机、不含网络调用、不依赖模型输出。
- 同一输入在任何机器上必须产出同一份报告——这一点由 `verify_all.py` 用 30 组输入输出向量逐字节比对来保证。
- 开发人员为此专门给报告日期加了 `FIRE_GEN_DATE` 环境变量：默认取当天，复现比对时固定为指定日期。
- 确定性检查在实际开发中直接抓出过真 bug：某技能因集合迭代顺序不稳定，同一输入两次生成会给出不同排序的结果，已修正为按模块库既定顺序输出。

### 4. 边界写在明处

每一份报告末尾都有固定免责声明：本系列只做法规条文的结构化整理与主动提示，不替代消防技术服务机构的现场判定，也不构成法律意见；法规修订后以官方最新公布文本为准；具体执行口径以属地消防救援机构意见为准。

这不是免责话术。消防执法的地方差异极大——同样是消防控制室单人值守，苏州有苏消委办〔2024〕28号明确"远程操作条件下每班不少于一人"，多数地区则仍按每班两人执行。工具能做的是把当地条款摆出来，不能做的是替执法机构下结论。

## 三、三种引擎范式

| 范式 | 适用 | 做法 | 系列内应用 |
|---|---|---|---|
| **check** | 体检/评估/排查 | 规则库外置为 `rules.json`，输入文本 → 画像识别 → 逐条比对 → 缺失项按严重度分级 → 覆盖度评分 → Top N 行动清单 | 合规体检、隐患识别、设施巡检、智慧消防成熟度 |
| **gen** | 方案/预案/课件/计算 | 配方外置为 `recipe.json`，输入信息卡 → 参数解析 → 画像匹配 → 逐格计算/选件 → 成套交付（方案 + 待补清单 + 依据） | 远程值守方案、灭火器配置、预案生成、培训课件、火灾分类处置 |
| **qa** | 法规问答 | 知识库外置为 `kb.json`，关键词两级匹配（长词强命中 / 多短词组合）→ 命中给条文与出处，未命中诚实兜底并指引查询渠道 | 消防法规问答 |

三个范式的共同点：**知识放在 JSON 里，逻辑放在 Python 里**。改法规不用改代码，改代码不用碰条文。

## 四、五道质量闸门

每个技能包发布前必须全部通过：

1. **自包含冒烟测试**——包内 `scripts/smoke_test.py`，不依赖外部路径与网络，覆盖三档输入（信息完整 / 部分缺失 / 触发红线）
2. **合规扫描**——外部绝对路径、价格词、规范化换行等红线项检查
3. **打包**——`pack_skill.py` 产出 zip，包根即技能根
4. **解压独立验收**——zip 解到干净目录再跑一次冒烟，确认自包含
5. **LF 规范化**——报告输出统一 `newline="\n"`，避免跨平台差异

系列级别另有一道：`verify_all.py` 全量复现，覆盖引用清单自检、30 组输出向量比对、10 个包冒烟汇总、出处覆盖率核验。

## 五、可验证制品

| 制品 | 位置 | 说明 |
|---|---|---|
| 可核验引用清单 | `_foundation/evidence/citation-manifest.json` | 28 条，含查证入口与现行状态 |
| 一键复现脚本 | `_foundation/evidence/verify_all.py` | 引用自检 + 向量复现 + 冒烟汇总 + 覆盖率 |
| 证据摘要 | `_foundation/evidence/EVIDENCE.md` | 自动生成，含制品 SHA-256 指纹 |
| 系列设计底座 | `_foundation/methodology.md` | 即本文档的上游版本 |
| 逐包可验证制品说明 | 各包 `references/verifiable-artifacts.md` | 本包向量清单、核验命令、边界声明 |

任何人克隆该目录后执行 `python _foundation/evidence/verify_all.py`，即可在自己的机器上重现证据摘要中的全部数字。

## 六、已知的局限

说清楚这些，比说优点更有用：

1. **覆盖不全。** 系列覆盖的是社会单位日常消防管理的常见场景，不含建设工程消防设计审查验收、消防产品认证、火灾事故调查等专业领域。
2. **地方差异靠人工维护。** 23 个地区的消防控制室值班规定逐条整理，但地方立法更新频繁，引用时务必核对该地最新版本。
3. **不接入实时数据。** 没有联网查询官方标准库的能力，标准状态依赖人工复核（每次系列升级复核一次）。
4. **不做数值承诺。** 例如 D 类金属火灾的灭火剂配置，国家标准明确"由研究确定"，系列内只给方法学指引、不给具体数量。
5. **不是执法依据。** 输出的整改建议、隐患定级仅供参考，最终以属地消防救援机构认定为准。

## 七、版本与复核

- 法规状态每次系列升级时复核一次，变更同步更新规则库并记入各包 CHANGELOG
- 引用清单新增条目时，必须同时提供公开查证入口，否则不予收录
- 发现条文引用错误（含废止、代替、条号错误）属于最高优先级缺陷，立即修复并全系列排查
